# 12｜多通道接通路線與 decision_state 判定契約

> **這份是給 UT 客服平台的規格提案，不是行銷文件。**
> 撰寫時遵守平台既有紀律：每一節標註北極星編號、最小編碼（能接既有零件就不新寫）、
> 不估時程、不做財務預估、不新增功能；所有未經量測的宣稱一律寫「尚未取得活證」。
> 需 Wilson 裁定的事項集中在第七節。

## 一、分期接通路線（N6 中台抽象）

| 期 | 通道 | 角色 | 對應北極星 |
|---|---|---|---|
| **第一期（現行）** | **LINE ＋ 網頁客服** | 唯一能長期培育的資產池 | N1 N2 N3 |
| **第二期** | **Facebook（粉專私訊＋留言）** | 捕捉器：把公開互動轉成一對一，再轉進 LINE | N6 N1 |
| **第三期** | **Instagram（DM＋留言＋限動回覆）** | 同上，但限制更嚴 | N6 N1 |

**接通順序的理由不是難易度，是「能不能留住人」**——見第二節。

## 二、通道能力硬限制（決定每個通道在漏斗裡能做什麼）

> 以下為 Meta 官方文件與多方一致彙整（查詢日 2026-09-19）。
> Meta 政策會變動，導入前請以 developers.facebook.com 當下公告為準。

| 能力 | LINE | Facebook Messenger | Instagram Direct |
|---|---|---|---|
| **主動推播給既有好友／聯絡人** | ✅ 可（計費） | ❌ 僅限 24 小時窗口內 | ❌ 僅限 24 小時窗口內 |
| **標準訊息窗口** | 無此限制 | **對方最後一則訊息起 24 小時**；窗口內可含推廣內容 | **同左，且更嚴** |
| **窗口外的例外** | — | Message Tag（**2026/4/27 起多數已停用**，送出回 error 100）；`HUMAN_AGENT` 7 天 | **僅剩 `HUMAN_AGENT`**：7 天、**必須真人發送**、需 App Review ＋ 商家驗證 |
| **留言轉私訊（Private Reply）** | — | 留言後 **7 天內、且只能發 1 則**；對方回覆後才重開 24 小時 | 同左；**IG Live 的留言只能在直播進行中回，結束即失效** |
| **主動私訊陌生人** | ❌ | ❌ 明文禁止 | ❌ 明文禁止 |
| **帳號門檻** | 官方帳號 | 粉專 | **必須是專業帳號（商業／創作者）** |
| **同時只能一個 App 控制對話** | — | ✅ thread control | ✅ thread control |
| **長期培育可行性** | ✅ | ❌ | ❌ |

### 由此推導出的三條設計原則

1. **FB／IG 不是培育通道，是捕捉通道。**
   它們的唯一任務是：在窗口內把人轉成 **LINE 好友** 或 **留下 Email／電話**。
   轉不過來的，過了窗口就是永久失聯——這不是文案問題，是平台物理限制。

2. **留言轉私訊「只有一發子彈」。**
   第一則私訊必須同時做完三件事：回答他問的、給他要的東西、請他加 LINE。
   寫得像「稍後將有專人與您聯繫」等於浪費掉唯一的一次機會。

3. **`HUMAN_AGENT` 不是自動化的延長線。**
   它必須由真人發送，用於「issue 無法在 24 小時內解決」的客服情境；
   拿去跑自動化序列會被 API 擋下並構成政策違規。
   → **平台端應在超過 24 小時的對話上，把自動回覆能力關閉，只開放真人介面。**

## 三、身分與「一個人一列」（N1；遵守 R-7）

平台現行條文 R-7：members 以（品牌、通道、帳號座標、userId）為鍵；寫入端一律經 `members.account_id_for`。
平台「明確不做」清單含：**未經審核的跨品牌會員合併**。

**因此跨通道身分規則如下（不改 schema，符合最小編碼）：**

| 情況 | 處理 |
|---|---|
| 同一人在 LINE、FB、IG 各有一列 | **正常，不自動合併** |
| 想把三列視為同一人 | 只在**同一品牌內**、且有明確關聯證據（同一支手機、同一 Email、本人於對話中確認）時，建立 `linked_contact_group`，**不覆寫原列** |
| 跨品牌 | **不合併**（已是明確不做事項） |
| 合併依據 | 一律記錄 `link_source`（本人確認／同 Email／同手機）與時戳，可回溯、可解除 |

> **設計理由**：跨通道合併錯誤的代價，是把 A 家屬的長輩資訊顯示給 B 家屬看。
> 在長照場景這不是體驗問題，是事故。寧可重複，不要錯接。

## 四、`decision_state` 七欄位判定契約（N2→N3）

> 平台現況：七欄位已定義、每輪已寫入，但**只有 `current_goal` 與 `route_depth` 被用來改變行為**；
> `next_best_action` 只寫進 log；「高意圖捷徑」程式中註明**刻意不做，要 Wilson 先定契約**。
> 以下即為該契約的提案。

### 4.1 `service_mode`（服務型態）

| 值 | 判定 | 行為 |
|---|---|---|
| `info` | 詢問通則性資訊（補助流程、規格、價格） | 可全自動 |
| `personal` | 描述了自己或長輩的狀況 | **禁止自動生成同理句**，僅可回「我請同事親自回覆您」 |
| `incident` | 正在發生的走失／緊急事件 | **立即轉真人**，全程不提產品 |
| `support` | 已購後的裝置或帳號問題 | 自動查詢＋真人補位 |
| `b2b` | 場域、數量、導入、報價、API | 切 B2B 路線 |
| `out_of_scope` | 同業、學術、媒體、倫理不符 | 轉對應窗口，不佔業務管線 |

### 4.2 `lead_maturity`（線索成熟度）— 0 到 5

**原則：事件訊號權重遠高於瀏覽訊號。** 一個焦慮的照顧者可能只讀一篇就私訊；研究型讀者讀十篇也不會買。

| 值 | 名稱 | 判定條件（任一成立即達成） |
|---|---|---|
| 0 | `unknown` | 尚未辨識身分 |
| 1 | `browsing` | 已知身分（家屬／專業人員／通路／場域），但只問通則資訊 |
| 2 | `situational` | 描述了具體照顧情境（同住、外出狀況、長輩會自己出門） |
| 3 | **`triggered`** | **出現事件訊號**：曾走失、曾找不到人、近期開始迷路、機構發生離區事件、工廠發生工安事件、客戶投訴失溫 |
| 4 | `evaluating` | 主動問尺寸／到貨／怎麼買／補助怎麼申請／能不能場勘／要幾台 |
| 5 | `committed` | 已留可聯絡方式並同意聯繫，或已排定場勘／已進補助流程 |

**特別規則**：
- **事件訊號（3）可跳級**，不需經過 2。走失事件後 1–2 週是意願最高、也最短的時間窗。
- **`out_of_scope` 一律鎖在 0**，不因行為累積升級。
- 降級：14 天零互動且未達 4 → 降一級（避免分數只進不退造成管線灌水）。

### 4.3 `handoff_readiness`（可交接度）

| 值 | 條件 | 交給誰 |
|---|---|---|
| `none` | 自動化可完結 | — |
| `soft` | `service_mode = personal`，或同一問題重複 ≥2 次，或往返 ≥6 輪未解決 | 一般客服 |
| `hard` | `lead_maturity ≥ 4`，或對方主動要求真人，或涉及價格／客製／退貨 | 客服主管或業務 |
| **`urgent`** | `service_mode = incident`，或 `lead_maturity = 3` 且事件在 14 天內 | **立即真人** |
| `specialist` | B2B 且提到既有系統整合、環境條件、法規稽核 | 技術／場勘 |

> **鐵律（沿用平台「不准把程式存在推論成已完成」的精神）**：
> `lead_maturity ≥ 4` 只能由**真人對話確認後**寫入，不得由自動化直接判定。
> 自動化最高只能寫到 3。這條規則防止分數膨脹，也是報表可信的前提。

### 4.4 `next_best_action`（下一步）— 從只寫 log 升級為可執行

| 值 | 觸發 | 動作（**受 E-7「旅程不開發送」約束**） |
|---|---|---|
| `answer_inline` | `lead_maturity ≤ 1` | 自動回答完結 |
| `offer_tool` | `= 2` | 提供工具型資產（走失 SOP 卡／額度配置表／場勘準備清單），換取加 LINE 或留 Email |
| `human_now` | `= 3` 或 `handoff_readiness = urgent` | **排入人工佇列並標示優先**（不自動外發） |
| `qualify` | `= 4` | 真人補齊欄位（見第五節） |
| `route_sales` | `= 5` | 交業務／通路窗口 |
| `channel_migrate` | 通道為 FB／IG 且窗口剩餘 < 12 小時 | **在窗口內送出一次「加 LINE」引導**（這是 FB/IG 唯一的關鍵動作） |
| `close_kindly` | `service_mode = out_of_scope` 或不適配 | 送出轉介資訊並標記原因碼，停止銷售類接觸 |

> **與 E-7 的相容性**：以上所有 action 都只做「排入清單並在後台顯示」，
> 不觸發任何自動外發。送出開關維持關閉，由真人執行。

### 4.5 `current_goal` / `last_route` / `route_depth`（維持現行語意）

沿用現行「已在服務路線上就不把顧客丟回總選單」的用法，不變更。
唯一新增建議：`route_depth ≥ 3` 且 `lead_maturity ≤ 1` 時，視為**迷路**，寫入 `handoff_readiness = soft`。

## 五、機會捕捉欄位（N1；個資最小化）

### 5.1 一條必須寫進規格的法遵限制

《個人資料保護法》第 6 條將**病歷、醫療、健康檢查**列為特種個資，原則上不得蒐集。
**失智診斷、CDR 分級、巴氏量表分數屬於此類。**

> 🚫 **不要蒐集長輩的診斷資料。你們不需要它。**
>
> | ❌ 不要問 | ✅ 改成問 |
> |---|---|
> | 長輩的失智診斷等級？ | 長輩目前外出狀況是？ |
> | | → 需人陪同／可自行短程外出／曾自行外出迷路／曾走失需他人協尋 |
>
> 同一份資訊、零特種個資風險，而且**填答率更高**——家屬對「被問診斷」有防衛心，對「被問狀況」覺得被理解。

### 5.2 欄位清單（標註寫入者，避免 AI 推論污染判定）

| 欄位 | 必填 | 寫入者 | 影響 |
|---|---|---|---|
| `identity_track` | ✅ | 系統／客服 | 四軌分流（家屬／專業人員／通路／場域） |
| `channel_first` ＋ `short_url_code` | 系統 | 系統 | N5 歸因（接 09 的短網址命名規則） |
| `outdoor_status` | ✅（家屬軌） | 表單／對話 | **代替診斷欄位**，最關鍵的適配判斷 |
| `wander_event` | ✅（家屬軌） | 對話 | **`lead_maturity = 3` 的觸發器** |
| `caregiver_relation` | ✅（家屬軌） | 表單 | 是否為決策者 |
| `expectation_realtime` | ✅（家屬軌） | 對話 | **期待落差閘門**，見 5.3 |
| `site_scale` / `use_case` / `timeline` / `decision_role` | ✅（場域軌） | 表單／對話 | B2B 分級 |
| `existing_system` | 選填 | 對話 | 「需整合」→ 技術先評估，不得直接排場勘 |
| `preferred_contact` ＋ `contact_window` | ✅ | 表單 | 決定 SLA 通路與外撥時段 |
| `consent_marketing` ＋ 版本號 ＋ 時戳 | ✅ | 表單 | 無同意不得推播 |
| `disqualify_reason` | 條件必填 | 客服 | 停止銷售接觸；同時是產品路線圖的輸入 |
| 🚫 `elder_name` / `elder_id` / `diagnosis` | **禁止** | — | 成交／出貨／補助送件前一律不收 |

每個高權重欄位附 `_source`（表單／對話／AI 推論）與 `_confidence`。
**AI 推論的值不得單獨用於寫入 `lead_maturity ≥ 4`。**

### 5.3 期待落差閘門（本案唯一的必問題）

在家屬軌，於推進任何產品說明之前，必須先確認：

> 「我想先跟您確認一件事，免得之後失望——您心裡期待的，是像手機地圖那樣隨時打開就看得到位置？
> 還是『平常不用管、需要時能幫忙找到人』這種？這兩種東西不太一樣，我先講清楚比較好。」

- 答「定期回報可接受」→ 繼續
- 答「我要隨時看得到」→ 寫入 `disqualify_reason = 期待落差`，走誠實說明與轉介，**不硬推**
- 答「不確定」→ 用具體場景解釋後再問一次

> **這一題擋掉的成交，等於擋掉的退貨與負評。**
> 而在長照品類，負評是公開、永久、且會被 B2B 採購委員會 Google 到的。

## 六、自動化與真人的分界（N2）

**一句話原則：自動化負責「資訊」，真人負責「情緒與承諾」。**

**以及一條不可妥協的紅線：**
> 🚫 **AI／機器人不得對照顧者的照顧狀況做出判斷、建議或安慰式回應。**
> 機器人說「我理解您的辛苦」，被識破時造成的信任損害遠大於它節省的成本。
> 自動回覆可以**提供資訊**，但**不可扮演同理**。

### 四個硬觸發器（任一成立，立即中斷自動流程）

1. 情緒／事件詞：走失、不見、找不到人、跑出去、急、怎麼辦、撐不下去
2. 同一問題重複 ≥ 2 次（不要讓他問第三次）
3. 往返 ≥ 6 輪仍未解決
4. 主動要求真人 —— **零條件、零挽留、立即轉接**

### 通道別的額外規則

| 通道 | 規則 |
|---|---|
| FB／IG | **超過 24 小時窗口即關閉自動回覆能力**，僅開放真人介面（`HUMAN_AGENT`，7 天內） |
| FB／IG 留言轉私訊 | 系統須記錄該留言的 7 天到期時戳；**一則用完即鎖**，不得排入第二則 |
| IG Live | 留言私訊僅限直播進行中，結束即失效 —— 排程器須有此硬停點 |
| LINE | 無窗口限制，但受新資費影響（見第七節 F-6） |

## 八、本檔的紅燈自檢三問（依平台規格第三節要求作答）

1. **對應哪一條？**
   第一至三節 → N6 中台抽象；第四節 → N2→N3；第五節 → N1；第六節 → N2；第七節 → 治理。
2. **有沒有紅燈訊號？**
   無軸數膨脹（未新增北極星）；無對標其他公司的功能抄襲（僅引用平台政策硬限制）；無追最新技術；**無財務預估**。
3. **是不是最小編碼？**
   是。七欄位已存在、每輪已寫入、members 鍵值不變、不改 schema；
   本檔只補「判定規則」與「通道別的開關條件」，不要求新功能。
