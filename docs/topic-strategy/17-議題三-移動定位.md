# 17｜議題三：移動定位
## 「看得到車，看不到人」——長照移動段的無人區

> 依 Wilson 指示聚焦議題建設。本議題深挖議題二中只列為第③層、未展開的「移動定位」。
> 研究日期：2026-09-19

---

## 一、先解掉一個誤會：車載的三個技術疑慮，市場上已經有成熟答案

UTTEC 簡報把車載 Gateway 標為「依案 PoC 驗證**供電、耐震與網路**」。
這個謹慎是對的，但研究顯示：**這三題在市場上都已經是標準規格，不是未解難題。**

以已商品化的車載 BLE 閘道器（雲里物里 MG5、TOPFLYtech TLW2-6BL、Queclink GV620MG 等）為例：

| 疑慮 | 市場上的標準解法 |
|---|---|
| **供電** | **8V–52V 寬壓直流輸入**，直接吃車電；另配內建備用電池。外接電源線被切斷時會**立即上報告警** |
| **耐震／環境** | **IP67 防塵防水 ＋ IK10 抗衝擊**；工作溫度約 −20～60°C，冷鏈車可用 |
| **網路** | 隧道、偏遠路段斷網時**本地快取**，網路恢復後**自動重連並補傳**，不造成資料斷檔 |
| （附帶）金屬車廂屏蔽 | 專門設計以穿透廂體屏蔽，接收車內 BLE 標籤廣播 |

另一種架構（MOKO ＋ RAKwireless 的 BLE＋LoRaWAN 冷鏈方案）講得更直白：
資料記錄器裝在駕駛室，高速公路沒有網路覆蓋時把所有 BLE 日誌**快取進內建快閃記憶體**，
抵達目的地重連固定閘道後一次上傳——**「在拖車門打開之前就產生完整、不間斷的稽核追蹤」**。

> **研究判斷**：車載 Gateway 的 PoC 重點不該再放在供電／耐震／網路，
> 而該放在 **① 標籤回報密度夠不夠 ② 車內外的判讀邏輯（人在車上 vs 剛下車）
> ③ 與既有派車／核銷系統怎麼介接**。
>
> 這個修正值得寫進對外內容：**敢講「這三件事業界已經解決了」的廠商，專業感會立刻不同。**

## 二、移動定位的三種接收器：不是選一個，是分場景疊加

固定基礎建設覆蓋不到的地方，只能靠「會移動的接收器」。它有三種，取捨完全不同：

| | ① 車載 Gateway | ② 機構員工手機 App | ③ 群眾網路（路人手機） |
|---|---|---|---|
| 有沒有電 | **有**（吃車電） | 有（但耗手機電） | 有 |
| 有沒有網 | **有**（4G，斷線可快取） | 有 | 有 |
| 有沒有自身座標 | **有**（GPS／北斗） | 有 | 有 |
| 覆蓋範圍 | 車輛行經路線 | 員工走到的地方 | 人流所到之處 |
| 硬體成本 | 每車一台 | **零** | **零** |
| 可控性 | **高**（機構自有） | 中（要員工開 App） | **低**（密度不可控） |
| 適合場景 | 接送車、外出活動車、物流車 | 園區走動、外出活動隨隊、居家訪視 | 離開機構掌控後的**最後線索** |

**三者的正確關係是階梯，不是替代：**

```
在機構內      → 固定 Gateway（區域判讀）        ← 現行服務
在接送車上    → 車載 Gateway（連續、有座標）     ← 依案 PoC
隨隊外出      → 員工手機 App（零硬體成本）       ← 依案 PoC
脫離掌控之後  → 群眾網路（最後被偵測到的位置）   ← 現行服務，密度依賴
```

> 這個階梯圖本身就是一個很好的內容素材：
> **它誠實地標示了每一層的成熟度與限制，同時展示了沒有任何競品有完整四層。**

## 三、本議題最重要的發現：長照接送已經高度數位化，但**追的是車，不是人**

台灣的長照交通接送，數位化程度比想像中高很多：

| 事實 | 來源 |
|---|---|
| 2018 上半年已有 **1,896 輛**長照接送車、逾 **17 萬趟次** | 衛福部統計（引自 DRS 2020 服務設計研究） |
| 台北市社會局委託辦理「**長期照顧交通接送統一預約及管理服務方案**」，含民眾訂車介面、司機派遣 App、特約單位管理平台、機關後台、LINE OA，並串接車輛追蹤系統 | 康訊科技案例 |
| 大瑩長照導入智慧派車後：派案人員 **4 位→1 位**；月趟次 **約 1,200 → 2,300+**；效率提高 **1.8 倍**、零客訴、**一年省 150–180 萬** | ETtoday／物宇智能 |
| 服務設計研究發現：**超過 80% 乘客有 LINE 帳號**，因此以 LINE chatbot 作為預約與提醒主通道 | DRS 2020 |
| 司機 App 已有：行程提醒、路線班表、車輛檢查、追蹤導航、到站提醒、**電子簽名**、任務清單、乘客備註、里程報表 | 同上 |

**但把這些系統攤開來看，它們追蹤的全部是「車」：車在哪、車幾點到、車跑了幾趟。**

沒有任何一套在回答：

```
車到了 → 長輩有沒有上車？
上車了 → 中途有沒有自己下車？
到醫院了 → 長輩下車後走去哪裡？
回程時 → 該上車的人到齊了嗎？
```

### 3.1 一個具體到可以當標題的痛點

> 「很多司機在送長者到醫院之後，**可能會來不及按下 APP 就被警衛催促離開**，
> 導致司機回傳資料跟目的地不同，**最後變成無法申請補助**。」
> —— 物宇智能執行長葉耀中，ETtoday 2024-09-27

這段話表面是核銷問題，本質是**「人的行蹤沒有獨立證據，只能靠司機手動按鈕」**。

**如果長輩身上本來就有一顆會被車載接收器讀到的標籤，上下車就是自動事件，不需要司機按任何按鈕。**
這同時解決了三件事：安全、核銷、以及司機的操作負擔。

> 對照組：同類車載閘道器的規格書裡，校車場景明列的功能就是
> **「學生上下車考勤」**。同一個技術，換成長輩就是「上下車自動紀錄」。

### 3.2 為什麼這是無人區

| 玩家 | 守住哪裡 | 移動段 |
|---|---|---|
| 派車／核銷系統商（物宇、康訊、兌心、Jubo 等） | 車輛調度、預約、核銷、行政 | 追車不追人 |
| 機構內定位（Fusion、恆準、創鈺等） | 建築物內 | 出了大門就沒了 |
| 家用定位（GPS 手錶、防丟標籤） | 家屬自購 | 與機構系統不相通 |

**「長輩從機構走到車上、從車上走進醫院」這一段，三邊都沒接。**

## 四、移動段的三個場景，依可行性排序

| 序 | 場景 | 為什麼排這個順位 | 成熟度 |
|---|---|---|---|
| **1** | **日照接送車的上下車自動紀錄** | 需求最明確（安全＋核銷＋減少司機操作）、車輛數固定、單位願意付錢、且已有數位化底子可介接 | 車載需 PoC |
| **2** | **外出活動隨隊定位**（花博型場景） | 已有實際成功經驗（光田帶失智長輩去花博，靠手機定位找到人）、不需裝車、員工手機即可 | 機構 App 需 PoC |
| **3** | **請假外出／趁隙離開後的協尋** | 價值最高（有死亡案例），但最依賴群眾網路密度，也最容易期待落差 | 群眾網路為現行服務，須誠實說明 |

> **策略意涵**：對機構談移動定位，應該**從第 1 個場景切入**，不要從第 3 個切入。
> 第 3 個是最戲劇化的故事，但它是三者中最不可控的；
> 第 1 個是最不性感、卻最容易成交、也最容易做出可驗證成效的。

---

## 五、這個議題改變了什麼

1. **車載不再是「技術風險項」，而是「整合工作項」。** 供電／耐震／網路已有標準答案，PoC 的問題意識該換。
2. **移動定位的第一個商業落點不是協尋，是接送核銷。** 這是最快能算出 ROI 的一段。
3. **「看得到車，看不到人」是一句可以直接當標題用的產業洞察**，而且目前沒有人講過。
4. **員工手機作為接收器，是被嚴重低估的零硬體成本方案。** 它同時解決了外出活動與園區走動兩個場景。

# 七、研究者自行發起的延伸議題群集：A16 留存、轉介與口碑

> Wilson 授權「若我認為有留存價值可自行發起」。以下說明為什麼我認為值得建，並直接建出來。

### 7.1 為什麼這個群集非建不可

三個結構性理由：

1. **這個品類的廣告效率天生就差。** 前面的實證已經顯示：
   品類滲透率極低、關鍵字被外商內容站佔據、家屬討論場域破碎且被聯盟行銷污染。
   **在廣告打不動的品類裡，轉介與口碑不是加分項，是主要獲客管道。**
2. **這門生意有明確的留存斷點，但完全沒有內容在處理。**
   鞋墊含 3 年系統使用權 → 第 4 年是斷點；機構導入後 → 擴點、加購、續約是第二桶金；
   長輩狀況改變 → 換方案或退場。這些時刻目前是空白。
3. **機構與通路的轉介，是這個品類最強的擴散路徑。**
   一家日照中心導入成功，會被同區同業問；一個輔具店賣得好，會跟同業講。
   **B2B 的口碑傳播速度比 B2C 快，而且不需要廣告預算。**

### 7.3 這個群集的紀律

- **A16-01（第 4 年）在第 4 年的政策確認之前不得發布。** 它是留存斷點，也是信任地雷（見 `11` 攻擊 7c）。
- **A16-06、A16-12、A16-17 是自我檢討型內容。** 在一個充滿假評價的品類裡，這類內容的信任回報最高，但必須真的有內容可檢討，不能演。
